# project-spec

一个用于生成项目开发规范的 Agent Skill。给它一个陌生仓库，它读代码、反推真实技术栈与工程约定，产出一份能约束后续开发的规范文档（`CLAUDE.md` / `AGENTS.md`）。

产出的不是架构散文，而是"接下来在这个仓库里写代码该照什么做、什么绝对不能做"。

## 它解决什么问题

接手一个已有项目时，真正卡人的不是"用了什么框架"，而是这些没人写进文档的事：

- 列表接口的分页字段到底叫什么，前端怎么解包
- 新代码必须走哪个请求封装，哪些写法属于历史遗留、不能模仿
- 改了配置要同步哪个初始化脚本，漏了会让新环境装不上
- 哪些构建开关不能动，比如默认跳过测试

这些只能从代码里读出来。这个 Skill 把这件"只能靠读代码"的事，定义成一条有预算、有证据标准的固定流程。

## 快速开始

Skill 的目录名必须与 `SKILL.md` 里的 `name` 一致，因此整个目录要以 `project-spec` 命名。

```text
<skills 目录>/
└── project-spec/
    ├── SKILL.md
    ├── template.md
    └── probes.md
```

放到下列任一位置即可被自动发现：

| 位置 | 作用域 |
|------|--------|
| `.agents/skills/` | 项目级，随仓库共享 |
| `.cursor/skills/` | 项目级，随仓库共享 |
| `~/.agents/skills/` | 用户级，仅本机 |
| `~/.cursor/skills/` | 用户级，仅本机 |
| `.claude/skills/` / `~/.claude/skills/` | Claude 兼容目录，同样会被读取 |

项目级目录可以继续分子目录归类，Skill 的身份取自 `SKILL.md` 所在的那层文件夹，与父级分类名无关。放在仓库嵌套子目录里的 Skill 会被自动限定到该子目录范围内的文件。

触发方式有两种：描述任务让 Agent 自行匹配，或用 `/project-spec` 显式调用。会命中这个 Skill 的说法包括：

- 生成项目规范
- 分析这个项目
- 梳理开发规范
- 初始化 `CLAUDE.md` / `AGENTS.md`
- 给新项目写规范

不限定语言与框架，适用于单模块、多模块、前后端混合、微服务仓库。

## 文件说明

| 文件 | 作用 |
|------|------|
| `SKILL.md` | Skill 主体：五条铁律、执行预算、并行分工、四步流程、11 条自检清单 |
| `template.md` | 输出文档的章节结构与排版要求，成文严格按此输出 |
| `probes.md` | 与语言无关的探查方法：按生态找构建清单、按职责找约定、抽样规则、常见陷阱 |

## 核心设计

**只写有证据的结论。** 每条选型、版本、命令、约定都要能指向具体文件。版本号只从锁定文件或构建文件取，不凭印象。

**描述现状，不描绘理想。** 仓库里两种写法并存时，写"两套并存 + 存量保持、新代码用 X"，不单方面宣布一种。规范的价值是让新代码融入既有代码，而不是引发重构。

**拿不到就写"未发现"。** 没有 lint 配置就不写 lint 规则，没有测试目录就写未配置。空章节直接删除，不留占位。

**禁止项必须带原因。** 每条禁止对应真实踩坑、框架限制或安全要求，不拿通用最佳实践凑数。

**只读不改。** 全程只读探查，产出的只有文档，不动源码。

这五条同时约束了产出形态：可以没有某一节，但留下的每一句都要能被追问到底。

## 执行预算

主线程工具往返控制在 25 次以内，中等仓库（数千文件）总耗时 8 分钟以内。

预算集中花在两处值得重复验证的地方：**版本号**（必须回到锁定文件或构建文件）、**权限 / 路由 / 菜单的三方一致性**（前端判断、后端校验、初始化数据）。其余一次定性。

省预算靠"整类跳过"，而不是"每个文件都看快一点"。代码生成器产物、结构同构的样板文件、上游项目的 README，各取 1 个样本加 grep 确认多数派即可。

## 并行分工

仓库超过一个端时先派子代理铺开，主线程不下场做广度扫描：

| 角色 | 范围 |
|------|------|
| A 结构与依赖 | 目录树、构建清单的直接依赖与版本、启动入口、配置来源、部署文件 |
| B 核心契约 | 返回体、分页、基类、全局异常、鉴权入口、缓存封装 |
| C 客户端 | 构建配置、请求封装、路由、状态管理、一个列表页 + 一个表单页 |
| D 数据与运维 | 建表与初始化数据、权限菜单数据、版本控制状态、脚本与 CI |

子代理的返回契约写死在任务里：只回结论加 `文件:行号`，不贴完整文件；同类文件精读 1 个，其余用 grep 确认是否多数派，不一致才展开。主线程只负责合并证据、对冲突处定点复核、按模板成文。

## 产出结构

```text
# <项目名> 开发规范
1. 技术栈          —— 每端的选型与版本、环境、产物、部署形态
2. 常用命令        —— 真实存在的命令与不能擅自动的开关
3. 代码规范        —— 分层、出口层、业务层、实体、查询、配置、客户端、测试、安全、提交
4. 禁止            —— 按工程/服务端/客户端/数据与安全分组，每条带原因
附：改代码前的检查清单
```

篇幅 150~350 行，表格优先于散文。仓库里没有对应形态的章节整节删除，不留"本仓库不适用"这类占位。

有前端时，客户端部分会落到一张固定的"场景 → 必须这么写"对照表上，覆盖请求封装、列表解包、文件下载、权限判断、防重复提交、字典枚举、时间范围、分页、加载状态等——填的是仓库里的真实入口，不是通用建议。

## 交付报告

写完后会向使用者报告：文档路径、篇幅、哪些章节属于**推断**（需人工确认）、哪些地方因源码不可读而留空，以及本次探查开销（派了几个子代理、跑了几次构建命令、哪些类别的文件被整类跳过）。

推断项单独列出，方便逐条核对。这是文档可信度的关键，也是判断下次该不该调策略的依据。

## 边界

适合：给存量项目补一份可执行的规范，或给新接手的仓库做一次结构化摸底。

不适合：替代代码评审、生成架构设计文档、做代码迁移或重构方案。它只描述"现在该怎么写"，不规划"以后要改成什么样"。

## 注意

- 目标位置已有同名文档时不会直接覆盖，先读后询问是覆盖、合并还是另存为 `*.generated.md`。
- 非 git 仓库（SVN / Mercurial）会先判断版本控制类型，不默认按 git 处理。
- 源码加密或权限不可读时，文档中记录降级读取方式，而不是跳过核心文件。
